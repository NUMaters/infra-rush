# CPU難易度の自動調整

CPU戦が終わると、匿名の試合ID・選択難易度・CPU設定版・勝敗・経過時間・城HPをバックグラウンドで送る。結果画面の3択アンケートは任意で、同じ試合IDで結び付ける。名前、招待コード、端末識別子は収集しない。個々の試合と回答はFly.ioの非公開ボリュームに保管し、リポジトリへコミットしない。

GitHub Actionsの `Tune CPU difficulty` が毎日実行され、直近60日のデータを取得する。設定版は難易度ごとに記録し、別の難易度の調整によって集計がリセットされない。各難易度で現行CPU設定版の試合が80件以上、アンケートが15件以上ある場合だけ評価する。勝率と体感に十分なずれがあり、両者が矛盾せず、最後の更新から3日以上経過しているときに候補を作る。一度に変更するのは1難易度の判断間隔だけで、`master/cpu-balance-policy.json` の上下限・最大歩幅を守る。候補は旧設定との左右入れ替えCPU戦で検証し、逆効果が大きい場合は破棄する。テスト・ビルドが通ったら設定と集計要約をコミットし、GitHub Pagesを再デプロイする。

結果データはクライアント自己申告のため、厳密な勝率証明にはならない。アンケートは回答者の偏りがある。自動変更を小さく保ち、**同じCPU設定版の新しいデータを集め直してから次の変更をする**。学習済みの大規模モデルを使っているわけではなく、収集・評価・更新・記録・巻き戻しの運用基盤と、制約付きの自動チューナーである。

人が介入するときは `master/cpu-balance-policy.json` の `enabled` を `false` にして全体停止、または難易度ごとの `frozen` を `true` にする。目標勝率、体感目標、境界、最小サンプル数も同ファイルで調整できる。変更履歴は `docs/balance/history.jsonl` に追記される。問題がある設定は `master/cpu.json` を前のコミットに戻してPagesを再デプロイし、同時にその難易度を `frozen` にして再昇格を防ぐ。手動検証はGitHub Actionsの `workflow_dispatch` を使い、初期値の dry run では公開設定を変更しない。

公開後の自動調整にはFly.ioの `INFRA_BALANCE_EXPORT_TOKEN` とGitHub Actionsの `BALANCE_EXPORT_TOKEN` に同じランダム値を設定する。エクスポートAPIはこの値を持つ運用ジョブだけが読める。値をログやリポジトリへ残さない。サーバー側には `INFRA_FEEDBACK_PATH` と `INFRA_MATCH_PATH` を永続ボリューム上に設定する。
